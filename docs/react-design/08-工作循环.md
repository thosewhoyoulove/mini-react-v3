# 第 8 章：工作循环：向下 begin、向上 complete

[← 返回总目录](../../React设计与实现.md) · [上一章](./07-副作用标记Flags.md) · [下一章 →](./09-beginWork按tag分发.md)

---

把一棵组件树交给 Render 后，执行顺序并不是简单地从上往下。遍历到文本叶子时，方向会反转；遇到兄弟时，又会横向移动。如果时间片恰好在中途结束，下一次回调还要从断点接着走。`workInProgress` 和工作循环共同完成这件事。

## 8.1 一棵小树实际按什么顺序执行

仍用 `div → h1 / p` 这棵树。Render 留下的轨迹是：

```text
begin HostRoot → div → h1 → "Mini React"
complete "Mini React" → complete h1
begin p → "count: 0"
complete "count: 0" → complete p → complete div → complete HostRoot
```

向下时，`beginWork` 为当前 Fiber 计算 child，并把第一个 child 交给循环。走到 HostText 后已经没有 child，遍历转为向上。`completeUnitOfWork` 完成当前节点；若右侧还有 `sibling`，就从兄弟重新向下，否则沿 `return` 继续回到父节点。

这个顺序等价于递归调用“进入子节点”和“从子调用返回”，只是调用栈被显式指针替代。父节点总在孩子之后 complete，所以 Text 可以先创建宿主实例，`h1` 再把它装入自己的离屏实例；孩子的 flags 和 lanes 也能在此时向父节点汇总。

一路返回 HostRoot 后，`workInProgress` 变成 `null`。`finishRoot` 取出 `root.current.alternate` 作为 `finishedWork`，移除已经处理的 lanes，再进入 Commit。根上若还有其他 lane，提交结束后会继续调度。

## 8.2 一个工作单元如何决定下一步

`workInProgress` 指向下一格待处理 Fiber。`performUnitOfWork` 的主路径是：

```ts
const next = beginWork(
  current,
  unitOfWork,
  workInProgressRootRenderLanes,
);
unitOfWork.memoizedProps = unitOfWork.pendingProps;
unitOfWork.lanes = removeLanes(
  unitOfWork.lanes,
  workInProgressRootRenderLanes,
);

if (next == null) {
  completeUnitOfWork(unitOfWork);
} else {
  workInProgress = next;
}
```

`beginWork` 接收 current、这一轮的 WIP Fiber 和 `renderLanes`。返回 child 时，`workInProgress` 移到 child；返回 `null` 时，当前分支无法继续向下，`completeUnitOfWork` 接管方向。于是循环本身只需记住一格 Fiber，寻找 child、sibling 和 return 的细节分别留在 begin 与 complete 路径中。

`renderLanes` 表示这一轮准备处理的优先级。`beginWork` 据此检查节点和子树是否还有本轮工作，决定执行组件还是 bailout。处理成功后，相应 lane 从节点的 `lanes` 中移除，`pendingProps` 也成为本轮实际使用过的 `memoizedProps`。

`try/catch` 让异常路径也能给出明确的下一格。组件抛出 thenable 时，`unwindWork` 沿 return 寻找 Suspense；普通错误则寻找带 `isErrorBoundary` 的函数组件。边界得到 `DidCapture` 后，`workInProgress` 被指回该边界，下一次 `beginWork` 将渲染 fallback，而不是继续那条失败的分支。

## 8.3 同一段遍历如何暂停、续跑和重启

同步与并发路径处理 Fiber 的方式相同，差别只在循环条件：

```ts
function workLoopSync(): void {
  while (workInProgress != null) {
    performUnitOfWork(workInProgress);
  }
}

function workLoopConcurrent(): void {
  while (workInProgress != null && !unstable_shouldYield()) {
    performUnitOfWork(workInProgress);
  }
}
```

| 路径 | 更新入口 | 怎样投递 | 是否让出 |
| --- | --- | --- | --- |
| Sync | `root.render` 的 `SyncLane` | 微任务 | 不检查 `shouldYield`，一次走完 |
| Concurrent | 普通 `setState` 的 `DefaultLane`、`startTransition` 的 `TransitionLane` | Scheduler 宏任务 | 每个 Fiber 之间检查时间片 |

Sync 工作由微任务启动，进入循环后不会检查 `shouldYield`。DefaultLane 和 TransitionLane 由 Scheduler 回调启动，每处理一个 Fiber 都可能因时间片耗尽而退出。这里仍是主线程上的串行 JavaScript，只是在工作单元之间合作式让出。

让出时没有清空 `workInProgress`，它仍指向下一格待处理 Fiber。Scheduler 再次回调后，循环便从这一格继续。只有第一拍或已有结果失效时，`prepareFreshStack` 才从 `root.current` 准备新的 WIP 根；正常续跑不会重复创建起点。

暂停与重启处理的是两种情况。暂停只因时间片用完，半成品仍然有效；重启则发生在 Render 期间又到达同档或更高优更新时。已经 begin 过的节点可能没有读取这次新入队的 Hook 更新，`rootNeedsRestart` 会让调度器放弃半成品，从 current 根重新准备 WIP。较低优先级的更新继续留在 `pendingLanes`，等这一轮提交后处理。

## 本章回顾

- `beginWork` 向 child 深入；叶子返回 `null` 后，`completeUnitOfWork` 借 sibling 和 return 完成整棵树。
- 一个 Fiber 是一次可暂停的工作单元，`workInProgress` 始终保存下一格，Concurrent Render 仍运行在主线程。
- 时间片耗尽会保留半成品续跑；同档或更高优更新会使已读取过旧队列的半成品失效，从 current 根重启。
