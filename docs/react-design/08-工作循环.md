## 8.1 `performUnitOfWork`

全局指针 `workInProgress` 指向「下一个该处理的 Fiber」。处理一格只做四步：

```ts
function performUnitOfWork(unitOfWork: Fiber): void {
  const current = unitOfWork.alternate;
  let next = beginWork(current, unitOfWork);
  unitOfWork.memoizedProps = unitOfWork.pendingProps;
  unitOfWork.lanes = removeLanes(unitOfWork.lanes, workInProgressRootRenderLanes);
  if (next == null) {
    completeUnitOfWork(unitOfWork);
  } else {
    workInProgress = next;
  }
}
```

1. **`beginWork`**：按 tag 接上 `child` 链表，返回第一个 child（或 `null`）。
2. **`memoizedProps = pendingProps`**：这个节点的 props 本轮已经用过，Commit 对比属性时读 memoized。
3. **清掉本轮 lane**：这个节点上属于 `renderLanes` 的更新已处理，避免下一轮重复。
4. **有 child → 下一单元是 child**（深度优先往下）；**没有 → 转入 complete**。

「一个工作单元 = 一个 Fiber」，切片才能停在节点边界，而不是停在函数半中间。

## 8.2 没有 child 就 complete，有 sibling 就横走

`completeUnitOfWork` 的顺序和递归的「函数返回」一样：

```text
先 completeWork(自己)     创建实例、冒泡 flags
有 sibling → 下一单元是兄弟，return（父节点还没 complete）
没 sibling → 回到父节点，父节点也 complete
一直升到 HostRoot，workInProgress 变成 null → Render 结束
```

```ts
function completeUnitOfWork(unitOfWork: Fiber): void {
  let completedWork: Fiber | null = unitOfWork;
  do {
    completeWork(completedWork.alternate, completedWork);
    const siblingFiber = completedWork.sibling;
    if (siblingFiber != null) {
      workInProgress = siblingFiber;
      return;
    }
    completedWork = completedWork.return;
    workInProgress = completedWork;
  } while (completedWork != null);
}
```

对着第 6 章那棵树走一遍：

```text
begin HostRoot → begin div → begin h1 → begin "Mini React"（叶子）
complete 文本 → complete h1 → sibling 是 p
begin p → begin "count: 0"
complete 文本 → complete p → 无 sibling
complete div → complete HostRoot → wip = null
```

深度优先、先子后兄再父。`completeWork` 能 `appendAllChildren`，正是因为走到父节点时，孩子的 `stateNode` 已经建好。

Render 整棵走完：`finishRoot` 取出 `root.current.alternate` 当 `finishedWork`，进入 `commitRoot`。然后 `ensureRootIsScheduled`：`pendingLanes` 若还留着更低优，再约一轮。

## 8.3 sync 与 concurrent

两套循环共用 `performUnitOfWork`，差别只在**能不能在切片边界停下**：

```ts
function workLoopSync(): void {
  while (workInProgress != null) {
    performUnitOfWork(workInProgress);
  }
}

function workLoopConcurrent(): void {
  while (workInProgress != null && !unstable_shouldYield()) {
    performUnitOfWork(workInProgress);
  }
}
```

| | `workLoopSync` | `workLoopConcurrent` |
| --- | --- | --- |
| 谁走 | `SyncLane`（`root.render`） | `DefaultLane`（`setState`） |
| 投递 | `queueMicrotask` | Scheduler 宏任务 |
| 让出 | 不问 `shouldYield` | 每单元问一次，5ms 到了就停 |
| 断点 | 无 | `workInProgress` 停在下一节点，再 `ensureRootIsScheduled` |

`prepareFreshStack` 从 `root.current` 克隆一棵新 WIP。Sync 插队、同档重启、第一次 render 都走它——半成品 WIP 上已经 `beginWork` 过的节点看不到新的 hook 队列 / props，必须丢弃从根重来。

concurrent 路径三种出口：

1. 跑起来时已经有 Sync → 转微任务。
2. 时间到了、树没走完 → 再约一拍宏任务，从断点继续。
3. `workInProgress == null` → `finishRoot` → commit。

调度细节（谁约、谁 cancel、高优怎么插队）见第 17、18 章。下一章先把 `beginWork` 按 tag 的四条路拆开。

## 面试复习

### 一句话结论

工作循环把一次 Render 拆成逐 Fiber 的 `beginWork` 向下和 `completeWork` 向上；同步与并发路径复用同一单元逻辑，只在是否检查让出时机上分叉。

### 面试回答

为什么要设计工作循环？递归渲染无法把控制权稳定地交还调度器，而 Fiber 已把树变成显式链表，所以可以把一个 Fiber 定义为一个工作单元。`performUnitOfWork` 先执行 `beginWork` 生成或复用 child；没有 child 时，`completeUnitOfWork` 依次完成自己、寻找 sibling、再沿 return 回溯，最终在 HostRoot 收束并进入 Commit。本仓库中 `SyncLane` 由微任务触发 `workLoopSync`，不会检查 `shouldYield`；`DefaultLane` 由 Scheduler 宏任务触发 `workLoopConcurrent`，在工作单元边界检查是否超过时间片，暂停后靠全局 `workInProgress` 续跑，遇到同档或更高优更新则从根重启。官方 React 的并发循环还处理 suspended、errored、completed 等更多退出状态，并不等同于“每 5ms 必然执行一次”。

### 常见追问

**1. 为什么 `completeWork` 必须在孩子之后？**

父宿主节点需要收集已经完成的子实例，父节点的 `subtreeFlags` 也依赖孩子先把副作用冒泡上来。

**2. 时间片用完后如何恢复？**

循环退出时不清空 `workInProgress`，下一次 Scheduler 回调继续处理它；若有使当前结果失效的新更新，则丢弃半成品并从 current 根重建 WIP。

**3. 并发模式是否多线程执行 Render？**

不是。本仓库仍在主线程串行执行 JS，只是将工作分散到多个宏任务，在节点边界合作式让出。

**4. 为什么 Sync 通过微任务仍不算时间切片？**

微任务只决定何时开始；开始后 `workLoopSync` 不调用 `shouldYield`，会连续处理到整棵树完成。

### 容易说错

- 不要说 concurrent 等于并行；这里是单线程、合作式调度。
- 不要说“每个 Fiber 固定耗时 5ms”；5ms 是本 Scheduler 对一批工作的让出阈值，不是单节点预算。
- 不要说暂停可以发生在任意函数指令处；本仓库只在两个工作单元之间检查 `shouldYield`。
- 不要说高优更新总能复用当前半成品；本仓库同档或更高优到来会标记重启，从 current 根重新准备 WIP。
