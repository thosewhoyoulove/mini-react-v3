# 第 8 章：工作循环：向下 begin、向上 complete

[← 返回总目录](../../React设计与实现.md) · [上一章](./07-副作用标记Flags.md) · [下一章 →](./09-beginWork按tag分发.md)

---

`root.render` 把一棵描述交进来之后，Render 并不是从根排到叶子就结束。走到文本叶子，方向转向上；右边还有兄弟，就再向下。时间片在中途用完时，下一拍要从停下的那一格继续。`workInProgress` 记着这一格，工作循环负责移动它。

## 8.1 一棵小树实际按什么顺序执行

仍用第 6 章那棵树：`div` 下面是 `h1` 和 `p`。Render 留下的轨迹是：

```text
begin HostRoot → div → h1 → "Mini React"
complete "Mini React" → complete h1
begin p → "count: 0"
complete "count: 0" → complete p → complete div → complete HostRoot
```

指针一次只停在一格。`beginWork` 给当前 Fiber 接上 child，并返回第一个 child。工作循环把 `workInProgress` 移到这个 child，于是路径向下。HostText 没有 child，`beginWork` 返回 `null`，`completeUnitOfWork` 接管。

`completeUnitOfWork` 做的事和递归函数返回时一样，只是父指针写在 `return` 上：

1. 对当前节点调用 `completeWork`。
2. 右边还有 `sibling`，就把 `workInProgress` 指到兄弟，这次向上停住。下一轮再对兄弟 `beginWork`。
3. 没有兄弟，就沿着 `return` 回到父节点，在同一次调用里继续 complete 父节点。

所以 `h1` 的文本 complete 之后，马上 complete `h1` 自己。`h1` 右边还有 `p`，父节点 `div` 先不 complete。等 `p` 这一支也走完，没有兄弟了，才连续 complete `p`、`div`、`HostRoot`。

父节点总在孩子之后 complete。原因是父 DOM 要装入已经建好的子 DOM，孩子的 flags 和 lanes 也要在这时汇总上来。文本可以先 `createTextInstance`，`h1` 再把它装进自己的离屏实例。这些实例还没进文档。

升到 HostRoot 后，它的 `return` 是 `null`，`workInProgress` 变成 `null`，循环结束。`finishRoot` 取出 `root.current.alternate` 当作 `finishedWork`。此时 `workInProgress` 已经空了，完成的那棵树挂在 current 根的 alternate 上。接着从 `pendingLanes` 里去掉本轮处理过的 lane，进入 Commit。根上若还有别的 lane，提交结束后 `ensureRootIsScheduled` 会再约一次。

## 8.2 一个工作单元如何决定下一步

`performUnitOfWork` 处理「当前这一格」。主路径是：

```ts
const next = beginWork(
  current,
  unitOfWork,
  workInProgressRootRenderLanes,
);
unitOfWork.memoizedProps = unitOfWork.pendingProps;
unitOfWork.lanes = removeLanes(
  unitOfWork.lanes,
  workInProgressRootRenderLanes,
);

if (next == null) {
  completeUnitOfWork(unitOfWork);
} else {
  workInProgress = next;
}
```

`current` 是 `unitOfWork.alternate`，也就是屏幕上那一棵里的对应节点。第一次挂载时，很多节点还没有 alternate，这里就是 `null`。

`beginWork` 返回 child，`workInProgress` 就移到 child。返回 `null`，当前分支不能再向下，`completeUnitOfWork` 去找兄弟或父节点。循环自己只保存一格 Fiber。找 child、sibling、return 的细节分别留在 begin 和 complete 里。

`memoizedProps` 和 `lanes` 在决定向下还是向上之前就写好。原因是这一格针对本轮 `renderLanes` 的工作已经做完，孩子是下一格的事。`pendingProps` 因此成为本轮用过的 props。对应 lane 从这一格的 `lanes` 里去掉，避免下一轮把同一件工作再做一遍。`childLanes` 不在这里清，它要等 complete 时从孩子汇总。

让出点在 `performUnitOfWork` 的前后，不在它的内部。向下时，一次调用只 begin 一个节点。向上时，一次 `completeUnitOfWork` 可能连续 complete 多个祖先，中间不再询问时间片。原因是父节点 complete 时，孩子必须已经完成。结果就是：很重的一次 `beginWork`（比如一个大组件函数）不会被从中途拆开。

`try/catch` 包住 begin 和 complete。子树里抛出的异常也要给出明确的下一格，不能让 `workInProgress` 停在失败的那一格。

`unwindWork` 从出错节点的 `return` 往上找：

1. 抛出的是 thenable（带 `then` 的对象）：停在还没有 `DidCapture` 的 Suspense 上，打上这个标记，弹出边界内部的 Provider，并把 `workInProgress` 指回该边界。同一个 thenable 只补订一次。它完成后，用捕获时的那一档 lane 再调度这个边界；没有 lane 时退回 `DefaultLane`。
2. 普通错误：停在带 `isErrorBoundary` 的函数组件上，同样打 `DidCapture`，把错误放进 `updateQueue`。
3. 找不到边界：原错误继续抛出。

下一轮 `beginWork` 看到 `DidCapture`，就调和 fallback，不再继续失败的那一支。

## 8.3 同一段遍历如何暂停、续跑和重启

同步与并发处理 Fiber 的方式相同。差别在循环条件和这次工作怎么被约出去：

```ts
function workLoopSync(): void {
  while (workInProgress != null) {
    performUnitOfWork(workInProgress);
  }
}

function workLoopConcurrent(): void {
  while (workInProgress != null && !unstable_shouldYield()) {
    performUnitOfWork(workInProgress);
  }
}
```

| 路径 | 更新入口 | 怎样投递 | 是否让出 |
| --- | --- | --- | --- |
| Sync | `root.render` 的 `SyncLane` | 微任务 | 不检查 `shouldYield`，一次走完 |
| Concurrent | 普通 `setState` 的 `DefaultLane`、`startTransition` 的 `TransitionLane` | Scheduler 宏任务 | 每个工作单元之前检查时间片 |

`root.render` 和别的 Sync 更新进 `queueMicrotask`。同一次事件里来了多次，只约一个微任务，后到的只改 `syncRoot`。微任务执行时走 `workLoopSync`，不问 `shouldYield`。

`DefaultLane` 用 Scheduler 的 `NormalPriority`，`TransitionLane` 用 `LowPriority`。两条都进 `performConcurrentWorkOnRoot`，所以都会切片。Scheduler 在宏任务开始时把截止时间设成「现在 + 5 毫秒」。`unstable_shouldYield` 只比较现在是否已经到了这个截止时间。

这里仍是主线程上的串行 JavaScript。让出的办法是合作式的：循环自己退出，把下一格留在 `workInProgress` 上。Scheduler 再次回调后，如果这格还在，并且没有要求重启，就不会再 `prepareFreshStack`。

有三种情况会重新从 `root.current` 做一棵 WIP，而不是接着上一格：

1. 并发路径的第一拍，`workInProgress` 还是 `null`。
2. Sync 插进来。`performSyncWorkOnRoot` 先把 `workInProgress` 置空，再 `prepareFreshStack`。原因是并发半成品上已经 begin 过的节点，看不到这次 Sync 的新 props 和 Hook 队列。并发回调如果发现 `pendingLanes` 里已经有 `SyncLane`，这一拍直接返回，改约微任务。
3. Render 期间又来了同档或更高优的更新。`shouldRestartCurrentRender` 把 `rootNeedsRestart` 设为 true。更低优的更新只并进 `pendingLanes`，不设这个标记。

重启标记不会让正在执行的那一格立刻跳回根。`workLoopSync` / `workLoopConcurrent` 内部不看它。等这一拍的循环退出（同步路径会把树走完，并发路径也可能是时间到了），外层发现标记，就把 `workInProgress` 置空，并且不调用 `finishRoot`。这一轮的 WIP 不提交。下一次调度再从 current 根准备 WIP。

根上如果同时有 `SyncLane` 和 `DefaultLane`，`getNextLanes` 只取出最高的一档。这一轮走 Sync。Default 留在 `pendingLanes` 里，等这次 commit 之后再约。

## 本章回顾

- `beginWork` 向 child 深入。叶子返回 `null` 后，`completeUnitOfWork` 先完成自己，有兄弟就转去兄弟，没有就沿着 `return` 向上。
- 让出点在 `performUnitOfWork` 之间。向上收尾时，同一次调用可能连续 complete 多个祖先。Concurrent 仍跑在主线程上，一拍大约 5 毫秒。
- 时间片用完会留下 `workInProgress` 续跑。Sync 插队，或同档、更高优更新，会丢掉半成品，从 current 根重来。更低优更新留在 `pendingLanes`。

对应实现在 `packages/react-reconciler/src/workLoop.ts` 的 `performUnitOfWork`、`completeUnitOfWork`、`workLoopConcurrent` 和 `performConcurrentWorkOnRoot`。
