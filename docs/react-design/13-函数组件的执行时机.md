# 第 13 章：函数组件什么时候执行

[← 返回总目录](../../React设计与实现.md) · [上一章](./12-Commit三阶段.md) · [下一章 →](./14-Hook链表与Dispatcher.md)

---

写下 `createElement(App)` 时，只是把 `App` 这个函数放进 React Element，并没有执行它。Commit 阶段改的是宿主树、ref 和 Effect，也不会回来调用组件。真正的调用在 Render。沿着一次 Counter 的 render 往下看，可以把组件函数、Fiber 和 Hook 串起来。

## 13.1 组件函数只负责产生 children

```js
function Counter() {
  const [count] = useState(0);
  return createElement('p', null, 'count: ' + count);
}
```

Render 处理 Counter Fiber 时，`beginWork` 进入 `updateFunctionComponent`，再交给 `renderWithHooks`。到这里 `Counter(props)` 才执行。返回值是下一层 children，也就是一份 `<p>` 的元素描述。DOM 还没有产生，要等 complete 创建离屏节点，再等 Commit 插入或更新。

函数执行结束后，`count` 这个局部变量跟着这次调用结束。需要跨 render 保留的数据由 Counter 对应的 Fiber 记住：

```text
fiber.memoizedState → Hook0 → Hook1 → ...
```

函数组件 Fiber 的 `stateNode` 通常是 `null`。Hook 链挂在 `memoizedState` 上，不要和宿主节点的 `stateNode` 混在一起。同一个 `Counter` 在页面里出现两次，会得到两个 Fiber。每个 Fiber 各自一条 Hook 链，状态彼此独立。

## 13.2 `renderWithHooks` 怎样建立执行上下文

`renderWithHooks` 不会一上来就调用组件。它先做四件事，再进入函数体：

1. `currentlyRenderingFiber` 指向本轮正在构建的 WIP Fiber。第一个 Hook 要写到它的 `memoizedState` 上。
2. 把 WIP 上一次留下的 `memoizedState`、`updateQueue`、`dependencies` 清空，两个链表游标也置空。本轮的 Hook 链从头接。上一轮如果中断，半成品链就在这里丢掉。
3. 选择 Dispatcher。`current == null`，或者 current 上还没有 Hook 链（`memoizedState == null`），用 mount 表。否则用 update 表。
4. 在 `try` 里执行组件。普通函数组件调用的是 `Component(props)`，不传 ref。ForwardRef 才把 `fiber.ref` 作为第二个参数。

`finally` 里会把 Dispatcher 和 `currentlyRenderingFiber`、两个游标都清空。组件正常返回或中途抛错，都会清。原因是这些变量是模块级的，不清掉就会漏到下一个组件。抛错之后，半截 Hook 链可能还留在 WIP Fiber 上；下一轮如果重新执行，步骤 2 会再次把它置空。

也因为这套上下文只在组件执行期间存在，在组件外调用 `useState(0)` 时，Dispatcher 是 `null`，会抛出：

```text
Invalid hook call. Hooks can only be called inside function components.
```

ForwardRef 和 Memo 最后也会进 `renderWithHooks`。Memo 可能先比较 props，比较通过就 bailout，组件函数不会执行。一旦执行，Hook 用的仍是同一套 mount / update 上下文。

还有一种情况，组件函数根本不会被调用。props、ref、context 都没变，自己和子树也没有本轮 lane 时，`beginWork` bailout，直接复用 current 的 child。这和 Effect 的 deps 没变不是一回事。deps 没变时，组件已经执行了，只是没有给 Fiber 打上 `Update` 或 `Passive`，Commit 不会跑这次 effect。bailout 则连函数都跳过，里面的 `useState` 也不会被调用。

只使用 `useContext`、没有任何普通 Hook 的组件，`memoizedState` 一直是 `null`。更新时仍会选中 mount 表。两张表的 `useContext` 都指向 `readContext`，读到的值相同。这一格为什么不占 Hook 链表，下一章再讲。

## 13.3 顺序为什么是 Hook 的身份

Hook 没有名字，也不看局部变量叫什么。React 只看它在这次执行里是第几次调用：

```text
Hook0  第一次 useState
Hook1  useRef
Hook2  useEffect
```

更新时，current 链和 WIP 链从头逐格对齐。条件分支会把后面的 Hook 错接到前面的格子上：

```js
if (visible) {
  useState(0);
}
useEffect(sync, []);
```

上一轮 `visible` 为 `true` 时，链表是「useState，useEffect」。`useEffect` 的 destroy、deps 在第二格。下一轮 `visible` 变成 `false`，函数里第一次调用变成了 `useEffect`。update 路径仍从旧链第一格取出数据，读到的是上一次的 state，不是 effect。链表没有名字可以重新搜索。

本实现在本轮调用次数多于上一轮、current 链已经走完时，抛出 `Rendered more hooks than during the previous render`。Hook 变少时，这里没有再做官方 React 那种开发期检查。本轮只把实际调用到的格子克隆到 WIP，current 上多出来的旧格子不会跟着过去。提交之后，新的 current 就是这条更短的链。报错只挡住「越调越多」的情况。每轮保持相同的调用顺序，两轮状态才对得上。

## 本章回顾

- 函数组件在 Render 的 `beginWork` 里由 `renderWithHooks` 调用，返回 children。Commit 不再执行它。
- 局部变量只属于一次函数调用。跨 render 的 Hook 数据在对应 Fiber 的 `memoizedState` 链上。
- bailout 会跳过整个组件函数。Effect 的 deps 没变时，组件已经执行，只是本轮不登记 Effect。
- Hook 靠调用位置对齐。条件里增减 Hook，会让后面的调用读到旧链上错误的那一格。

源码可以从 `packages/react-reconciler/src/beginWork.ts` 的函数组件与 bailout 分支看起，再到 `packages/react-reconciler/src/hooks.ts` 的 `renderWithHooks`。
