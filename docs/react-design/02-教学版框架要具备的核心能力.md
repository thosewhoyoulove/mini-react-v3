## 2.1 整页重建会堵住主线程

先把最省事的声明式运行时写出来。下面是为了暴露问题而省略属性、事件和错误处理的伪代码，不是本仓库实现，也不能直接替代 React：

```js
function render(element, container) {
  container.innerHTML = '';
  mount(element, container);
}

function mount(element, parent) {
  if (typeof element.type === 'function') {
    mount(element.type(element.props), parent);
    return;
  }
  const node = document.createElement(element.type);
  parent.appendChild(node);
  const children = element.props.children;
  const list = Array.isArray(children) ? children : [children];
  for (const child of list) {
    if (child == null || child === false) continue;
    if (typeof child === 'string' || typeof child === 'number') {
      node.appendChild(document.createTextNode(String(child)));
    } else {
      mount(child, node); // 子树不返回，这一层就出不去
    }
  }
}
```

输入是一棵 Element 描述和一个 DOM 容器。输出是按描述重新创建的整棵 DOM 子树：旧内容先被清空，每个后代再通过递归 `mount` 创建。点 reverse 时，`setItems` 若直接调用这样的 `render`，主线程就要等整棵树创建完才回到浏览器。树一小看不出来。树一大，输入和绘制都要等这趟递归结束。

要在中途停一下，停的位置必须是「下一个节点」，而不是一次深递归的半中间。`mount` 做不到：它要等子树全部 `appendChild` 完，函数才返回，调用栈上没有「下次从兄弟节点继续」这种记录。

所以描述树还得再变一种形状。节点用指针串起来，做完一个就问「时间还够不够」，不够就把「下一个节点」记在变量里，下次接着做。这种节点就是后面的 Fiber，工作循环在第 6、8 章。什么时候该让出主线程，是第 17 章的事。

本仓库已经把「这次有多急」和「这段 JS 何时占主线程」拆开了，但本章先不展开档位。只记住一个能在 demo 里核对的事实：文件末尾的 `root.render` 会把首屏一次做完；点 `+1` 或 reverse 走的是 `setState`，不在点击回调里把整棵树同步走完。

## 2.2 边算边改 DOM 时不能把半成品露在屏幕上

上面的 `mount` 还有第二个问题。它一边递归一边 `appendChild`。假如第 2.1 节真的允许它在中途返回，屏幕上会留下一棵没建完的树：有的 `<li>` 已经是倒序后的新节点，有的还是旧的，或者直接缺了一截。

算的那份结构就不能是用户正在看的那份。准备两份：

```text
current         已经提交、屏幕上对应的那棵
workInProgress  这一轮正在算的那棵
```

这一轮的比较、打标记，以及创建尚未插进文档的宿主节点，都发生在 `workInProgress` 上。本仓库的 `completeWork` 可以先创建离屏 DOM，但整轮算完进入 Commit 后，才会修改已挂载的文档并切换根的 `current`。没算完就停住时，停的是内存里的指针，用户看到的页面仍是上一轮提交的结果。

代价是同一逻辑位置最多保留 current 与 work-in-progress 两格 Fiber，并维护两者之间的对应关系。换到的是：计算可以停、可以丢掉重来，用户看不到半棵列表。这里说的是本仓库的简化模型，不是“两份完全独立的 DOM”，也不是对官方 React 内存占用的量化结论。节点怎么配对、提交时根怎么对调，第 6 章和第 12 章对着 `fiber.ts` 走。

## 2.3 决定怎么改的代码不该认识 document

`mount` 里直接写了 `document.createElement`。这样「孩子该不该复用」和「浏览器里怎么插节点」焊在同一个函数里。测试想换成内存节点，或者以后接到别的宿主，都得改调和过程。

本仓库把后一件事收成一份由外部传进来的宿主实现。`react-dom` 的入口负责组装，自己不遍历 Fiber：

```ts
// packages/react-dom/src/client.ts
export function createRoot(container: Element) {
  ensureRootClickDelegation(container);
  const root = createContainer(container, hostConfig);
  return {
    render(element: ReactElement) {
      updateContainer(element, root);
    },
  };
}
```

`createContainer` 把 `container` 和这份 `hostConfig` 记在根上。之后创建节点、插入、改属性，调和器都通过这组函数问宿主，不自己写 `document`。`document` 出现在 `packages/react-dom` 和 demo 里。打开 `packages/react-reconciler`，不应该看到它。

三件事合在一起，就是后面各篇的入口，不是本章要讲完的实现：

```text
能在节点之间停下    Fiber 链表和工作循环     第 6、8 章
算的时候不改屏幕    current / workInProgress  第 6、12 章
调和器不认识 DOM    HostConfig                第 19～21 章
```

下一章先看这些代码为什么要拆成几个包。不拆的话，`useState` 会把上面第三条缝重新焊上。

## 面试复习

### 一句话结论

声明式运行时至少要能在节点之间暂停、在屏幕之外把下一帧算完，并且把「算出什么变化」和「怎样改宿主」分开。

### 面试回答

如果每次更新都递归建完整棵 DOM，大树会占住主线程，而且递归调用栈上没有「下一个节点」可以保存，中间停不下来。如果边算边改已经显示的 DOM，一停就会露出半成品，所以计算要落在另一份结构上，提交完成再切换。如果调和过程和 `document.createElement` 写在一起，同一套比较就没法换宿主，也没法单独测。本仓库用 Fiber 保存工作进度，用 current / workInProgress 分开「屏幕上的」和「正在算的」，用 `createRoot` 把 DOM 实现注入调和器。首屏 `render` 和之后的 `setState` 急迫程度不同，具体怎样切片留到调度那一篇。

### 常见追问

**1. 为什么暂停更新要先改数据结构？**

暂停点必须落在节点边界上。递归 `mount` 要等整个子树返回才能回到父节点，中间没有地方记下「下次从谁继续」。

**2. 两份结构是不是两份 DOM？**

主要是两份用来计算的节点。屏幕上仍是已经提交的那一份宿主树。还没提交的实例可以先在内存里建好，但不作为用户看到的结果。

**3. 计算可以停，提交为什么要一次做完？**

计算写在另一份结构上，停了或丢掉都不改屏幕。提交会改用户看得到的宿主，做到一半停住，界面就会处在两帧之间。

### 容易说错

- 本仓库不是每次 `setState` 都在点击回调里同步走完整棵树。首屏 `render` 和之后的更新不是同一条急迫程度。
- 双缓冲保证的是「没提交完就不切换已显示的那棵」。提交阶段本身仍是一串宿主操作。
- 调和器不写 `document`，不表示它和宿主无关。它依赖一份宿主函数表，只是不依赖某一份 DOM 实现。

### 源码入口

- `packages/react-dom/src/client.ts`：把 DOM 宿主实现交给 `createContainer`。
- `packages/react-reconciler/src/fiber.ts`：两份树怎么配对，第 6 章再走。
- `packages/react-reconciler/src/workLoop.ts`：一次更新怎么被跑完或停下，第 8 章再走。
