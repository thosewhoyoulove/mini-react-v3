声明式把「界面是什么」留给应用，把「怎么改到那一步」留给框架。框架若只是「每次把整棵 DOM 拆掉再建」，心智负担是降了，性能和正确性却撑不住。本仓库刻意留下三块骨架，后面各篇都围着它们展开。

## 2.1 可中断的更新：为什么需要时间切片

浏览器一帧大约 16ms。若一次 `setState` 必须在同一个任务里把整棵树 reconcile 完，大树会把输入和绘制堵死：点了按钮，画面要等整轮算完才动。

教学版把「这次更新有多急」和「这段 JS 何时占用主线程」拆开：

| 问题 | 谁回答 | 本仓库落点 |
| --- | --- | --- |
| 这次更新多急？根下一次约哪档工作？ | Lane | `fiberLanes.ts`：`SyncLane` / `DefaultLane` |
| 这段工作何时跑、跑多久、能不能让出？ | Scheduler | `Scheduler.ts`：MessageChannel + 5ms `shouldYield` |

两条更新路径已经够讲清分叉：

```text
root.render  → SyncLane    → queueMicrotask → workLoopSync（一口气走完）
setState     → DefaultLane → Scheduler 宏任务 → workLoopConcurrent（可切片）
```

可中断的前提是：**工作单元必须能停在「下一个节点」，而不是卡在一次深递归的半中间。** 所以 ReactElement 那棵嵌套对象树，必须先变成 Fiber 链表——下一节和第 6 章会讲。没有链表，就没有「做完一个节点就问 `shouldYield`」。

教学版不追求官方那十几档 Lane 和优先堆。只要能讲清：**高优可以改变根的投递方式并重启半成品，低优路径可以让出主线程**，后面的工作循环、Hooks 队列才有落脚点。本仓库没有按 Lane 跳过 Fiber 或 Hook Update；Lane 在这里主要用于根级调度。

## 2.2 双缓冲：屏幕上永远是完整的一棵树

可中断带来第二个问题：若 Render 直接改正在显示的那棵树，切片中途屏幕上会露出半成品——少了几个子节点、属性改了一半。

做法是准备两棵树：

```text
current        屏幕上那棵，commit 之前只读
workInProgress 正在算的那棵，Render 只改它
alternate      两棵树上成对节点互相指
```

Render 阶段在 WIP 上 diff、打 flags、创建尚未插入的宿主实例。整棵走完才 `commitRoot`：先改 DOM，再 `root.current = finishedWork`。角色对调之后，刚才的 WIP 变成新的 current；下一次更新复用原来那格 current 当新的 WIP。

这样屏幕永远只看到**完整提交过的一棵树**。半成品停在内存里，切片暂停也只是 `workInProgress` 指针停在下一个 Fiber，DOM 不动。

`createWorkInProgress` 第一次会 new 一对、互相指；之后复用同一格 WIP，只清 flags / deletions。双缓冲的成本是大约两倍 Fiber 节点，换回的是可中断与「提交原子性」。

## 2.3 宿主无关：调和逻辑与 DOM 实现分离

调和器问的是「这棵 Fiber 要插、要删、要改属性」，并不该写死 `document.createElement`。否则同一套 begin / complete / commit 无法复用到别的宿主（Canvas、终端、测试环境）。

本仓库把「怎么碰真实世界」收成 `HostConfig` 接口，由 `react-dom` 注入：

```text
react-reconciler          只调 hostConfig.createInstance / appendChild / …
        ▲
        │ 注入
react-dom/hostConfig.ts   里面才出现 document / addEventListener
```

`completeWork` 创建实例、`commitWork` 插删改，一律 `getHostConfig()`。教学版只实现 DOM 这一套；换一套 config，调和逻辑不用改。第 19 章列完整能力清单。

三块能力合在一起，就是后面各篇的地图：

```text
可中断  → Fiber 链表 + Scheduler + Lane     （第 6、8、17、18 章）
双缓冲  → current / WIP / commit 切根       （第 6、12 章）
宿主无关 → HostConfig + react-dom           （第 19～21 章）
```

下一章先把仓库怎么拆包装清楚，避免读源码时找不到「这段逻辑属于哪一层」。

## 面试复习

### 一句话结论

教学版保留 Fiber 可暂停遍历、current/WIP 双缓冲和 HostConfig 三条主骨架，用最少机制串起调度、完整提交与跨宿主复用。

### 面试回答

为什么需要这三块能力？声明式更新若仍递归跑完整棵树，会长时间占用主线程；若边算边改 DOM，暂停时会暴露半成品；若调和器写死 DOM，又无法复用核心算法。因此数据结构上用 Fiber 的 `child/sibling/return` 把递归拆成工作单元，并用 `alternate` 连接 current 与 WIP；阶段上先在 WIP 完成 Render，再同步 Commit；宿主操作则通过 HostConfig 注入。本仓库的 `root.render` 走 `SyncLane`，`setState` 默认走 `DefaultLane`，后者由 Scheduler 约宏任务并按工作单元让出；`fiber.ts` 管双缓冲，`hostContext.ts` 和 DOM host config 隔离宿主。官方 React 有更多 Lane、并发能力、恢复与错误处理；本仓库只演示两档优先级和单根模型，不能把它等同于完整 Concurrent React。

### 常见追问

**1. 时间切片为什么依赖 Fiber？**

因为必须保存「下一步处理哪个节点」。Fiber 把递归调用栈显式化为指针和全局游标，完成一个节点后才能检查是否让出。

**2. 双缓冲是否意味着两份 DOM？**

不是。主要是两套 Fiber 节点；宿主实例通常通过 `stateNode` 复用或在完成阶段创建，屏幕上只有提交后的 DOM 结果。

**3. Render 可中断，Commit 为什么不可中断？**

Render 只计算内存结果，可以丢弃或续跑；Commit 会产生用户可见的宿主副作用，中断会暴露不一致界面。

**4. HostConfig 的收益只有支持 React Native 吗？**

不只。它把「算出什么变化」与「如何落实变化」隔开，也便于测试和理解 reconciler 的职责边界。

### 容易说错

- 不要说本仓库所有更新都时间切片：`SyncLane` 一口气完成，只有 `DefaultLane` 走并发循环。
- 不要把教学版两档 Lane 说成官方完整优先级模型；官方还处理过期、纠缠、转换等复杂语义。
- 不要说双缓冲保证整个更新过程“原子化”；它保证提交前 current 不切换，Commit 本身仍是同步副作用序列。
- 不要说 reconciler 完全不知道宿主能力；它知道 HostConfig 接口，只是不依赖 DOM 的具体实现。

### 源码入口

- `packages/react-reconciler/src/fiber.ts`：Fiber 指针、FiberRoot 与双缓冲。
- `packages/react-reconciler/src/workLoop.ts`：同步/并发循环与根调度。
- `packages/react-reconciler/src/fiberLanes.ts`：教学版两档 Lane。
- `packages/scheduler/src/Scheduler.ts`：宏任务调度与 `shouldYield`。
- `packages/react-reconciler/src/HostConfig.ts`：宿主能力接口。
- `packages/react-dom/src/hostConfig.ts`：DOM 宿主实现。
