# 中文技术书自然润色 Skill

## 目标

把“信息都对，但读起来像自动生成的提纲”改成可以连续阅读的技术文章。

润色不是简单换词，也不是一味缩短。完成后应同时满足：

- 读者能沿着问题、例子和源码自然向前走；
- 相邻章节各自回答一个问题，不反复讲同一套机制；
- 代码、图示和表格都承担解释任务，而不是装饰版面；
- 教学实现、生产实现和作者判断分得清；
- 修改后的技术结论能由源码或实际运行结果支持。

默认读者了解 JavaScript 和常见前端 API，但没有读过所讲框架的源码。

## 一、先审稿，不要立刻改句子

通读目标章节及前后各一章，先回答四个问题：

1. 这一章只需要解决哪个核心问题？
2. 读者进入本章前已经知道什么？
3. 哪个最小例子能让读者先看到现象？
4. 哪些内容与相邻章节重复，应该回指而不是重讲？

随后核对相关源码、测试和构建配置。旧文中的结论只能作为线索，不能当成事实来源。尤其检查：

- 功能是否已经新增或删除；
- 调度、事件、Effect 等时序是否改变；
- 教学实现是否被误写成官方 React 的行为；
- 文中的代码片段能否对应当前文件和函数。

## 二、让文章沿一条因果链前进

推荐的推进方式是：

```text
可观察的现象
  → 读者会产生的问题
  → 最小代码或数据结构
  → 源码怎样处理
  → 为什么这样设计
  → 只在必要处说明限制
```

这是一条思考顺序，不是必须逐项出现的文章模板。不要每节都写“先看一个例子”“分为三步”“这意味着”。

开头应尽快出现具体矛盾。例如：

- 调用了 `setState`，为什么当前变量没有改变？
- `createElement(App)` 为什么没有执行 `App`？
- 文本 Fiber 已经发现变化，DOM 为什么仍是旧值？

接下来直接进入能回答这个问题的代码。避免先列一页术语，再回头解释它们之间的关系。

## 三、代码与解释必须相邻

代码块之后立即说明三件事：

1. 输入或前提是什么；
2. 源码执行了什么；
3. 为什么得到这个结果。

不要把一段代码逐行翻译成中文，也不要隔两节才解释它。

图示适合表达树、链表、队列和时间线。表格只在确实需要横向比较时使用，例如两种 Lane 的投递方式。若一段自然语言更容易读，就不要为了“看起来完整”改成表格。

## 四、控制章节结构

- 每章通常保留不超过 3 个编号核心节。
- 一个小节只解决一个主要问题。
- 使用 VitePress 等已有页面目录时，不再在正文重复“本章书签”。
- 章末可保留简短“本章回顾”，通常 2–4 项；不要把正文改写一遍。
- 不使用“面试复习”“一句话结论”“Q/A”作为每章固定结尾，除非整本书本来就是面试手册。
- 页面已有上一章、下一章导航时，不必再用机械的“下一章我们将……”收尾。
- 源码入口可以就近写入正文；若放在章末，应采用一句自然的阅读路径，不连续多章复制同一清单模板。

结构一致不等于句式相同。相邻章节的开头、过渡和结尾应根据各自问题自然变化。

## 五、减少 AI 味的具体方法

### 少用高频套话

重点搜索并判断这些词是否真的必要：

- “当前仓库”
- “这意味着”
- “因此”
- “这里需要注意”
- “边界”
- “不能 / 不要”
- “一句话”
- “先看一个最小例子”

它们不是禁词，但连续出现会让文章像规则汇编。能让主语直接做动作时，优先直接写：

```text
生硬：这里需要注意，当前仓库的 Update 没有 lane 字段。
自然：这份实现的 Update 只保存 action 和 next，没有 lane 字段。
```

### 让主语保持具体

少写“进行处理”“完成调度”“实现更新”之类抽象组合。明确是谁做了什么：

```text
抽象：更新会在后续阶段完成处理。
具体：Commit 读到 Update flag 后调用 commitTextUpdate，文本节点才发生变化。
```

### 调整句子节奏

- 用短句交代关键动作，用稍长的句子解释因果。
- 一段通常 2–5 句，不要每句都单独成段。
- 不连续使用相同句式开头。
- 少用加粗替代逻辑；真正重要的结论应由前文推导出来。

### 把限制放在会误解的位置

不要每段都提醒“教学版不同于官方”。只在读者可能错误外推时说明一次：

```text
这份实现会在 Mutation 中同步清理被删子树的 Passive Effect；
生产 React 的删除路径更复杂，不能用这里的时序概括所有版本。
```

限制说明应服务于理解，而不是打断主线。

## 六、处理跨章节重复

同一机制只在最合适的一章完整推导一次。后续章节需要它时，用一句回指，然后讲新增内容。

例如：

- Flags 章完整解释 `subtreeFlags` 如何冒泡；
- `completeWork` 章不再重画同一棵树，转而解释 `childLanes` 和 `return` 指针为何也在这里修正；
- Scheduler 章讲 callback 如何排序和让出；
- Lane 章只说明更新优先级如何映射到 Scheduler，不重新讲一遍最小堆。

完成一组章节后，应连读相邻章节，而不是只逐文件检查。

## 七、编辑后校验

至少执行以下检查：

1. 每章是否仍有清晰的核心问题；
2. 第一个例子能否让读者预测结果；
3. 是否存在重复书签、固定问答、机械预告；
4. 相邻章节是否重复完整例子、图或结论；
5. 关键时序和数据结构是否仍与源码一致；
6. Markdown 标题、代码围栏、相对链接是否有效；
7. 文档站点能否构建。

可用文本搜索辅助发现模板残留，但不能用词频代替人工阅读。最后应再请一位独立审阅者只检查两件事：阅读是否自然，事实是否准确。

## 输出要求

向用户汇报时说明：

- 哪些阅读障碍被移除；
- 哪些跨章节重复被合并；
- 是否发现并修正事实错误；
- 实际运行了哪些文档构建或结构检查。

不要用“已全面提升”“达到出版级”等无法验证的评价代替具体改动。
