# 清晰技术写作 Skill

## 写作理念

目标是让具备必要基础的读者真正理解一项技术，而非堆积专业词汇。借鉴经典中文技术教程中可观察的教学方法：问题驱动、循序渐进、最小例子、代码与解释相邻、适度对比、明确适用范围。独立表达，不模仿任何作者的个人口吻或复写原文。

## 执行步骤

### 1. 确定读者与范围

- 判断预期读者：初学、熟悉基础、深入源码。用户未指定时，默认了解 JavaScript 和常见前端概念，但不了解当前主题。
- 用一句话确定文章要回答的核心问题；再列出最多 3 个子问题。
- 把核心问题之外的扩展点留到文末，不用一篇文章覆盖整本书。
- 如涉及框架源码、规范、API、版本差异，核实事实，并说明版本或前提。无法核实的推断必须标明。

### 2. 用问题引出主题

- 开头优先给出一个具体疑问、看似矛盾的现象、报错或代码差异。
- 先说明这个问题为什么值得理解，避免空泛的背景、行业趋势或口号。
- 可以用一小段示例引出疑问，不要第一段就定义十几个术语。

### 3. 控制认知负担

- 先讲读者已知的旧方案，再引入新方案。
- 每个小节只解答一个明确问题；按「现象 → 原因 → 示例 → 小结」推进。
- 第一次出现专业术语：一句口语化解释 + 一句精确定义（确有必要时）。
- 使用短句、常见动词和具体主语；避免连续抽象名词。
- 一段通常 2–5 句话；段落较长时按思路自然拆分。
- 比喻只能辅助理解，之后要映射回准确的技术机制；不能以比喻代替事实。

### 4. 用最小可运行例子教学

- 优先提供能独立执行、可预测输出的最小代码；避免一上来展示真实业务中几十行实现。
- 根据需要使用「旧写法 / 新写法」「错误理解 / 正确理解」「输入 / 结果」对照。
- 每个代码块后紧接说明：输入是什么、发生了什么、为什么得到这个输出。
- 涉及异步，指出事件顺序；涉及 React，区分 render / commit、不同版本与并发模式；涉及浏览器 API，注明平台限制。
- 复杂主题按层推进：最小示例 → 运行流程 → 原理 → 边界 → 实际用途。
- 代码应经过逻辑检查；未运行的代码不得声称已测试。

### 5. 文章结构

根据题材选择，不机械填充所有标题：

**概念/原理文**

1. 问题的由来
2. 一个最简单的例子
3. 原因在哪里
4. 再看一个稍复杂的情况
5. 常见误解和边界
6. 小结

**API/上手教程**

1. 它解决什么问题
2. 最基本的用法
3. 常用参数和返回结果
4. 常见场景
5. 错误处理和注意事项
6. 参考资料

**源码剖析**

1. 从可观察的行为提出问题
2. 最小使用代码与预期结果
3. 相关数据结构
4. 关键调用流程（少量必要源码）
5. 为什么这样设计、有什么权衡
6. 版本限制与结论

## 文风约束

- 中文自然、平实、冷静；像一个讲清原理的工程师。
- 允许自然过渡语，如「先看一个例子」「问题出在哪里」「回到最初的问题」，但不能每段重复。
- 标题具体、可检索，少用夸张词（「史上最全」「彻底颠覆」「看完秒懂」）。
- 解释应严格区分事实、简化模型和个人判断。
- 避免口号式结尾、反复总结、显得像 AI 模板的套话。
- 不伪造权威、性能数据、引用或实验结果。
- 不连续复用任何特定作者的标志性表述，不宣称文章由其他作者撰写。

## 输出前自检

逐项检查并修改：

1. 前 150 字内是否出现一个清晰的问题或动机？
2. 读者能否从第一个代码示例预测结果？
3. 每段是否只传递一个主要信息？
4. 每一个重要结论是否能被例子、机制或可靠来源支持？
5. 专业术语是否在第一次出现时解释？
6. 是否交代必要的版本、前提和特殊情况？
7. 有没有误把简化教学模型当成完整实现？
8. 删除重复定义、空泛评价与不必要的修饰词后，意思是否更清楚？

## 用户可追加的写作参数

- `读者水平`：入门 / 进阶 / 源码
- `篇幅`：短文（600–1000字） / 标准（1200–2200字） / 深入（不限）
- `侧重点`：原理 / API / 工程实践 / 面试讲解
- `代码语言`：JavaScript / TypeScript / 其他
- `是否需要参考资料`：是 / 否
- `是否保留用户原文结构`：是 / 否

## 示例指令

“用 clear-technical-writing 写一篇《React Fiber 为什么要使用链表结构》。读者有 React 基础但不熟悉源码。先用递归遍历不能方便暂停的问题引出，再用最小对象结构解释 child、sibling、return，最后解释工作循环如何找到下一个工作单元。要求 TypeScript 示例，讲清简化模型与真实源码的区别。”
